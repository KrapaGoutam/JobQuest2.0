# JobQuest 2.1-PA — Production Acceptance Remediation Report

## Executive Summary

During initial operator production acceptance of JobQuest 2.1 (`main @ 4dcda58f7283865a6d4b9fe1e6615f6b71a1ff5b`), functional and UX gaps were identified in acceptance items B through H.

Remediation work was executed on branch `fix/2.1-production-acceptance-remediation`. All root causes have been diagnosed, remediated, and verified with focused unit and integration regression suites.

---

## Remediation Details by Acceptance Item

### B — Dashboard Goal: "No daily application goal configured"
- **Root Cause**: `apps/web/src/views/DashboardView.tsx` previously contained a ternary condition (`isManager && !owner ? Promise.resolve(null) : fetchGoalProgress(...)`) that suppressed `fetchGoalProgress` whenever a manager viewed the workspace dashboard without an explicit owner filter selected. Consequently, `goalProgress` was `null`, causing `calculateDailyGoalMetrics` to report `hasGoal: false` and rendering "No daily application goal configured". Additionally, `DashboardPanels.tsx` allowed personal daily goals to leak into workspace aggregate metrics.
- **Fix**: Removed the suppression in `DashboardView.tsx` so `fetchGoalProgress(ws, { userId: owner || null })` is always called. Under the Supabase RPC `rpc_get_goal_progress`, passing null for `p_user_id` coalesces to the authenticated actor, returning the manager's personal daily goal. Updated `DashboardPanels.tsx` so `isManagerAggregate` nulls out personal targets for workspace summary widgets while `DailyGoalCard` receives personal goals.
- **Regression Test**: Added test in `tests/unit/m9-dashboard.test.ts` (`scenario G`) verifying that an authenticated manager with no owner filter receives their active DAILY goal and renders target and progress without falling into the unconfigured state. Non-manager and explicit-owner behaviors were also re-verified.
- **Result**: PASS.

### C — Group by Date: Immediate Reset on Selection
- **Root Cause**: In `apps/web/src/components/applications/ApplicationsToolbar.tsx`, clicking "Group by date" simultaneously called `onGroupByChange?.(next)` (`setGroupBy('date')`) and `onGroupByMonthChange?.(false)` (`setGroupBy('none')`), due to legacy month-toggle callbacks. The conflicting `setGroupBy('none')` immediately cancelled the date grouping state.
- **Fix**: Removed the conflicting `onGroupByMonthChange` callbacks from the date and month toggle handlers in `ApplicationsToolbar.tsx`. Single source of truth is now maintained by `onGroupByChange`.
- **Rendered Behavior Test**: Added focused unit test in `tests/unit/m3-applications.test.ts` verifying that:
  - `None`: renders flat list with no day or month headings.
  - `Date`: renders actual day headings ("Today", "Yesterday", specific calendar dates) with applications under appropriate headings.
  - `Month`: renders month headings ("October 2026", etc.).
  - `Mutual Exclusivity`: Date and Month cannot both remain logically active.
- **Result**: PASS.

### D — Tasks & Follow-ups: Selection, Dismissal, and Recurrence
- **Root Cause**: Bulk selection bar only mounted after items were already selected, with no mechanism to select all visible tasks from an empty state. Dismiss dialog did not explicitly clarify that dismissing a recurring task ceases recurrence.
- **Fix**:
  - In `apps/web/src/views/TasksView.tsx`, added a "Select all" / "Deselect all" toggle button in the filter toolbar that operates strictly over visible active items on the current page (`items`).
  - Restricted selection to non-completed tabs (`tab !== 'completed'`).
  - Cleared `selectedKeys` on tab change (`onTabChange`).
  - In `apps/web/src/components/tasks/QueueRow.tsx`, updated Dismiss dialog description to conditionally render: `"It moves out of your active queue and stays in history. This follow-up will be dismissed and will not recur again."` when `task.recurrence_rule` is present. Canonical cancellation RPC (`cancelTask` -> status `CANCELLED`) remains unchanged.
- **Regression Test**: Added tests in `tests/unit/m6-queue-habits.test.ts` verifying bulk selection toggle, completed tab exclusion, and recurrence dismiss messaging.
- **Result**: PASS.

### E — Extension Tailor Resume: "Enter Manually" Default
- **Root Cause**: Radio button for resume mode in `popup.html` and `sidepanel.html` had `checked` on "Select existing", and `sidepanel.js` hardcoded `setResumeMode('existing')`, which triggered uncredentialed auto-generation attempts.
- **Fix**: In `popup.html` and `sidepanel.html`, changed default `checked` radio to `mode-resume-manual` ("Enter manually"), unhid `group-resume-manual`, and hid `group-resume-existing`. In `sidepanel.js`, updated initialization to check `sidepanel-mode-resume-manual` and call `setResumeMode('manual')`.
- **Regression Test**: Verified via `apps/extension/tests/sidepanel-logic.test.js` and markup validation that manual entry is the initial mode.
- **Result**: PASS.

### F — Extension: Pre-save Copy JSON
- **Root Cause**: Extension previously serialized only the initial raw page extraction (`captured`) on "Copy JSON". Any user edits made in the extension form prior to saving were lost, and if extraction was partial, JSON was incomplete.
- **Fix**: Updated `footer-copy-json` event listener in `apps/extension/sidepanel.js` to merge current form input values (`edit-company`, `edit-title`, `edit-location`, `edit-arrangement`, `edit-employment`, `edit-salary`, `edit-url`, `edit-source`) with `captured` before invoking `generateAIJobJson`. No application ID, no database save, and no existing database record is required.
- **Regression Test**: Added 3 unit tests in `apps/extension/tests/ai-job-json.test.js` verifying:
  - Fresh unsaved extraction produces valid schema 1.0 JSON with 0 database dependencies.
  - Form edits prior to saving are accurately reflected in the output JSON.
  - Already-known/duplicate job pages can copy JSON without re-saving.
- **Result**: PASS.

### G — Analytics Goals: Immediate Current-User Default
- **Root Cause**: Goals tab previously inherited the workspace-wide aggregate mode (`selectedMemberId === ""`), displaying an empty "Workspace goal pacing" card requiring an extra click to view individual goals.
- **Fix**: Added `useEffect` in `apps/web/src/views/AnalyticsView.tsx` so that navigating to the Goals tab with `selectedMemberId === ""` immediately defaults `selectedMemberId` to `currentUserId`. Added `currentUserId` prop wiring from `App.tsx`. If a manager chooses another member from the dropdown, that selection is preserved.
- **Regression Test**: Added unit test in `tests/unit/m15f-goals-member-selection.test.ts` verifying immediate current-user selection on Goals tab while maintaining authorized member switching.
- **Result**: PASS.

### H — Application Activity: Daily / Weekly Aggregation & Profile Timezone
- **Root Cause**: Activity chart only showed 12-week pacing. Daily aggregation was needed with profile-timezone date boundary semantics.
- **Fix**: Implemented `calculateDailyActivity` in `apps/web/src/lib/dashboard.ts` using canonical `dayKey(iso, tz)` and `addDaysKey`. Buckets applications over a rolling 14-day window. In `DashboardPanels.tsx`, added a segmented toggle (`Daily` / `Weekly`) switching the `PaceChart` dataset between 14-day daily activity and 12-week pacing.
- **Regression Test**: Added tests in `tests/unit/m9-dashboard.test.ts` verifying:
  - 14-day daily rolling series.
  - Profile timezone handling for applications near UTC midnight (e.g. 02:00 UTC landing on previous calendar day in CDT).
  - Toggling between daily and weekly datasets without mutating weekly pacing.
- **Result**: PASS.
