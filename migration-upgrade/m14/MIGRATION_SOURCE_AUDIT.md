## 1. Executive Findings: Production Architecture Correction

### 1.1 Neon PostgreSQL is the True Production Database
Historical documentation occasionally conflated JobQuest 1.0's local development/testing database with its production database. **The authoritative audit confirms:**
* **Production Database Engine:** **PostgreSQL** hosted on **Neon Serverless Postgres** (`neondb`).
* **Connection Model:** Node.js with raw `pg` client and parameterized SQL queries (`backend/src/postgres-db.js`, `backend/src/postgres-worker.js`).
* **Migration Mechanism:** Sequential SQL files in `backend/jobsearch/migrations/` (migrations `001` through `013`), managed by `backend/src/postgres-migrate.js`.
* **CITEXT Extension:** Enabled for case-insensitive unique email matching (`CREATE EXTENSION IF NOT EXISTS citext`).
* **Identity Mechanism:** `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` used in PostgreSQL (mapped dynamically from SQLite `INTEGER PRIMARY KEY AUTOINCREMENT` in `postgres-migrate.js`).

### 1.2 Role of SQLite in JobQuest 1.0
SQLite is **NOT** the production runtime database:
1. It served as a local development sandbox and rapid unit test fixture runner.
2. It provided an offline export/backup format (`backend/src/sqlite-backup.js`).
3. Historical data was transitioned from SQLite to Neon Postgres using `backend/src/sqlite-to-postgres.js` during legacy Round 6.
4. **M14 Rehearsal Impact:** Rehearsal migration tooling must consume the relational schema corresponding to the PostgreSQL production definition, while retaining compatibility with SQLite export fixtures where authorized for offline staging.

## 4. Key Behavioral & Security Findings

1. **User Identity & PIN Retirement:**
   - Legacy users authenticate with `pin_hash` (PBKDF2/SHA-256 in `backend/src/security.js`).
   - Under JobQuest 2.0 Option B architecture, **legacy PIN hashes must NEVER be migrated as passwords**.
   - Instead, legacy users receive a `legacy_claim_code` stored securely in `public.legacy_claim_codes`. Users claim their account by providing an email and new password adhering to JobQuest 2.0 standards.
2. **Tenancy Model (ADR-012):**
   - JobQuest 1.0 was implicitly single-workspace (multi-user on one DB instance with integer `user_id`).
   - All legacy records migrate into a dedicated, isolated workspace: **`"JobQuest (Migrated)"`** (`018f0000-0000-4000-8000-000000000001`).
   - Personal workspaces are provisioned separately so users maintain modern multi-workspace capabilities.
3. **Application Stage Decomposition:**
   - Legacy `stage` column overloaded pipeline position, terminal rejection, voluntary withdrawal, ghosting, and employer cancellation.
   - Decomposes deterministically into `(stage, state, outcome, closure_reason)`.
4. **Historical Event Backfill:**
   - Legacy `activities`, `timeline_events`, and `stage_history` merge into append-only `application_events` to power modern stage-duration, funnel, and time-in-stage analytics without fabricating timestamps.
5. **Notes & Career Journal:**
   - Legacy `notes` (migration 011) maps 1:1 into `journal_entries` (introduced in M13), preserving `note_type`, markdown body, application linkage, and pinned state.
